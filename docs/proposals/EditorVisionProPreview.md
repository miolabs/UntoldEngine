# Preview on Apple Vision Pro from the Editor — Plan

Status: stage A BUILT on 2026-10-06 (uncommitted on the worktree branch `feature/ui_redesign_visionpro`, cut from upstream develop `769186b`): 11 source files under `Editor/VisionPro/`, the app shell, the gates, 24 new tests (1212 in all, 0 failures); not yet tried on a headset. Written 2026-10-06. Stage 1.7c of the editor UI redesign (`EditorUIRedesign.md`), inserted at the user's request before the Assets and Console panels.

Question: how does the editor show the open scene in an Apple Vision Pro while the Mac keeps rendering it, so a level is checked in the headset without building and installing a visionOS app?

## TL;DR

macOS 26 renders immersive content for a nearby Apple Vision Pro ("Mac spatial rendering"): a Mac app declares a `RemoteImmersiveSpace` scene, draws it with `CompositorLayer` and Metal exactly as a visionOS app does, and the headset shows it after its wearer accepts a prompt. Apple's own example for it is a 3D modelling app previewing a scene. The engine already has the visionOS render path (`UntoldRenderer.createXR`, `updateXR`, `renderXR` per eye, and the loop in `UntoldEngineXR`), and all the parts of it that a loop needs are public, so the editor can drive the engine for the headset without an engine change.

What was verified on this Mac (M4 Max, macOS 27.0.1, Xcode 27.0) on 2026-10-06:

| | |
|---|---|
| `RemoteImmersiveSpace`, `CompositorLayer`, `LayerRenderer`, `ARKitSession(device:)`, `WorldTrackingProvider` | in the macOS SDK, `@available(macOS 26.0, *)` |
| `supportsRemoteScenes` | **true** on this Mac (read from a SwiftUI view inside an AppKit window, in a probe app) |
| A SwiftUI `App` with `@NSApplicationDelegateAdaptor`, the editor's own `NSWindow`, and only `RemoteImmersiveSpace` + `Settings` as scenes | launches, opens no extra window |
| Deployment target macOS 14 with `@_weakLinked import CompositorServices` / `ARKit` | builds; the frameworks are weak-linked (`LC_LOAD_WEAK_DYLIB`), so the editor still starts on macOS 14 and 15 |
| ARKit on macOS | only `WorldTrackingProvider` (the headset's pose); hand, plane, image and the other providers are `unavailable` on macOS |
| Immersion styles for a remote space | `.full` and `.progressive` (no passthrough); visionOS 26 release notes: `.progressive` crashes the Mac app, use `.full` |
| `openImmersiveSpace` called from a view hosted in the editor's AppKit window | works: the system presents its device picker in that window (seen 2026-10-06). The picker **traps when the process has no bundle identifier** and **refuses to connect when LaunchServices has no record of the app**: the editor must run as an app bundle (section 5, `scripts/dev-app.sh`) |

Requirements for the person: Apple Vision Pro on visionOS 26, the Mac on macOS 26 (Apple silicon), both signed in to the same Apple Account with Wi‑Fi and Bluetooth on, near each other. The headset asks to accept the connection. Known from Apple's release notes: artifacts where near objects overlap far ones; stalls on a poor Wi‑Fi; the stream ends if Travel Mode is on or a FaceTime call runs.

## 1. What the engine has

- `UntoldRenderer.createXR(...)` makes a renderer in stereo (`renderInfo.isXRStereoMode = true`, per-eye depth and HZB textures from `initSizeableResources()`), `updateXR()` runs one update (the same `runFrame` as the Mac viewport), `renderXR(commandBuffer:passDescriptor:viewMatrix:projectionMatrix:eyeIndex:)` draws one eye with the game-mode graph, `setXRCameraWorldPosition` writes the headset's position into the active camera so streaming and LOD follow it, `finalizeXRStatsAndMonitors` closes the frame.
- `UntoldEngineXR` (visionOS only, 1,100 lines) owns the loop: `queryNextFrame`, `predictTiming`, `startUpdate`/`endUpdate`, wait until the optimal input time, `startSubmission`, the device anchor from `WorldTrackingProvider.queryDeviceAnchor(atTimestamp:)`, once per frame the frustum and Gaussian culling and the splat sort, then per `drawable.views` the view matrix `inverse(originFromDevice × view.transform)` and `drawable.computeProjection`, `buildHZBDepthPyramid`, `encodePresent`, `endSubmission`. Plus what a preview does not need: PSVR2, spatial gestures, plane detection, environment lighting, recovery of ARKit providers.
- Everything the loop calls in the engine is public: `performFrustumCulling`, `executeGaussianFrustumCulling`, `executeGaussianPreprocess`, `executeRadixSort`, `buildHZBDepthPyramid`, `acquireUniformFrameSlot`, `tripleVisibleEntities`, `visibleEntityIds`, `cullFrameIndex`, `commandBufferSemaphore`, `renderInfo` and its fields, `initSizeableResources()`.
- `createXR` cannot be used by the editor: it makes a second renderer, re-initialises the shared `renderInfo`, and `initResources()` creates a camera and a light in the open scene. The editor keeps its one renderer and switches it: `renderInfo.isXRStereoMode`, `renderInfo.viewPort` (the eye's texture size), `initSizeableResources()`, and back when the preview ends. The layer is configured with the editor's own formats (`bgra8Unorm_srgb`, `depth32Float`, `.dedicated` layout, no foveation), so no pipeline is rebuilt.
- The editor's render extension (highlight, light icons, gizmo) stays out of the headset: while previewing it adds only the pass that clears the gizmo layer, as the locked preview of a game camera does.

## 2. Design

- **The app becomes a SwiftUI `App`** (`UntoldEditorApp: App` with `@NSApplicationDelegateAdaptor(AppDelegate.self)`); the `AppDelegate`, its `NSWindow`, menus and the `NSHostingView` stay as they are. The body holds the `RemoteImmersiveSpace` (on macOS 26) and `Settings`. A small SwiftUI view inside the editor keeps the `openImmersiveSpace` / `dismissImmersiveSpace` actions in a shared session object so the View menu can call them.
- **`VisionProPreviewSession`** (observable, shared): `idle`, `connecting`, `previewing`, `ending`; begins when the compositor hands the layer renderer over, ends from the menu, from the headset (layer invalidated) or when the scene is closed or played. While previewing: the viewport is a locked preview (no camera steering, no clicks on the scene, as with a game camera), the panels edit the live scene, undo works.
- **The headset stands where the editor's camera was** when the preview began: the device pose from ARKit (origin at the headset's start) is composed with the editor camera's position and yaw, so the first thing seen is what the Mac viewport showed. The editor camera's pose is put back when the preview ends. (`SceneRootTransform` is not used: it is the game's.)
- **The Mac viewport mirrors the left eye** while previewing: the loop blits the left eye into a texture after rendering, and the viewport's `MTKView` shows it through a mirror delegate instead of running the engine frame (the engine is driven by the headset's loop then, on its own thread, at the headset's rate). The eye's texture is letterboxed into the viewport.
- **The loop** (`VisionProPreviewLoop`): a thread like the visionOS template's, the steps above, with a frame source protocol in front of CompositorServices so tests drive it with textures of their own and read the pixels back, as the editor's render tests do.
- **Engine stereo switch** (`EngineStereo.enter(eyeSize:) / leave(viewportSize:)`): the three `renderInfo` writes and `initSizeableResources()`, on the main thread with the viewport paused.
- **Packaging**: deployment target stays macOS 14; the new sources import CompositorServices and ARKit `@_weakLinked` and are guarded with `#if canImport` and `@available(macOS 26.0, *)`; the menu item is shown only where `supportsRemoteScenes` is true. (The alternative, `-weak_framework` through `unsafeFlags`, is allowed in a root package but is not needed.)

## 3. Stages

- **A. Preview (this stage).** View > Preview on Apple Vision Pro (and Stop), the app shell, the session, the loop, the mirror, the stereo switch, the extension gate, tests. Files under `Sources/UntoldEditor/Editor/VisionPro/`. What it does not do: no input from the headset (gaze and pinch), no hand tracking (not available to a Mac), no passthrough (not available remotely).
- **B. Robustness and quality.** Reconnect after a dropped stream; the headset's frame rate in the status bar; render quality (`maxRenderQuality`); `.progressive` when Apple fixes it; a key to put the headset back at the editor camera (F frames the selection on the Mac, the headset follows).
- **C. Interaction from the headset.** Gaze and pinch arrive on a Mac too (`LayerRenderer.onSpatialEvent`, macOS 26): select by looking and pinching, move the selection with a pinch drag, with the Mac's hierarchy and Inspector following.
- **D. Into the engine.** Fold the macOS loop into `UntoldEngineXR` (`#if os(visionOS) || os(macOS)`) so any game built with the engine gets "Play on Vision Pro" from its Mac build, and the editor uses the engine's loop. An engine PR with Harold's review; the editor's loop is written so the move is a removal.

## 4. Decisions

- **D1 Minimum macOS.** Keep 14; weak-link the two frameworks. Bumping the editor to macOS 26 is simpler but drops every Mac that is not on 26 yet. Recommended: keep 14.
- **D2 Where the headset starts.** At the editor camera (position and yaw), eye height from ARKit. Alternative: at the scene origin. Recommended: the editor camera.
- **D11 The pointer is a second head** (the user's intent): while previewing its plain movement turns the view, the cursor hidden and held; the scroll and the pinch do nothing (the user's ask: only the look from the pointer, the keys move); the editor's orbit, pan and zoom wait. Alternatives: turn only while the right button is held (hard on a trackpad, and the pointer wanders out of the viewport unseen under full immersion); keep the orbit on the scroll (swings the wearer round a point ahead).
- **D10 Level flying with a headset on** (the user's ask): W and S along the floor, Q and E for the height, whatever the camera's tilt; the editor's own flying goes where the camera looks. The mouse still turns the camera about both axes.
- **D9 Steering and drawing take turns.** The keys and the mouse move the camera between the headset's frames, under a lock the loop holds while it draws the eyes; the main thread waits a few milliseconds at most. Alternative: a camera of the loop's own, copied from the editor's each frame, which the engine's render API does not allow (it reads the active camera).
- **D8 The head's position is not written into the camera** (what the engine's own loop does for streaming, LOD and shading): the camera is the ride, read back every frame; the head stays within a room of it, which is what those three then go by. Alternative: a separate ride record that the editor's steering updates, so the engine's write could stay; more code for a few metres.
- **D7 Flying while previewing (the user's ask, 2026-10-06).** The keys and the mouse fly the editor's camera, and the headset rides it; its own tracked motion applies on top. Turning with the mouse turns the world about the wearer, which can be uncomfortable: the user asked for it as a preview tool.
- **D3 What the Mac shows while previewing.** The left eye, mirrored. Alternative: the viewport frozen with a notice. Recommended: the mirror.
- **D4 Editing while previewing.** The panels edit the live scene; the viewport takes no camera or scene input. Alternative: everything frozen, as in Play. Recommended: panels live.
- **D5 Immersion.** `.full` only in stage A.
- **D6 Where the loop lives.** The editor in stage A (no engine change, no wait for a review); the engine in stage D.

## 5. What stage A does, as built (2026-10-06)

- `UntoldEditorApp` is a SwiftUI `App` with the delegate adaptor; the body holds `VisionProPreviewScene` (macOS 26) and an empty `Settings`. The delegate's window and menus are untouched (verified in a probe: the AppKit menu stays, no extra window).
- View > Preview on Apple Vision Pro (hidden where the Mac cannot, disabled while the game plays; "Stop the Preview on Apple Vision Pro" while asked for or shown). The camera submenu is disabled meanwhile; Play ends the preview first.
- `VisionProPreviewSession` (states unavailable / idle / connecting / previewing / ending): saves the editor camera's pose, shows the editor camera, sets the stereo flag, swaps the viewport's `MTKView` delegate for `VisionProMirror`, runs `VisionProPreviewLoop` on a thread; ends from the menu, from the headset (source ends), or when another camera becomes the active one (scene load); the pose is put back only when the same camera is still the active one.
- `VisionProPreviewLoop` on the engine's public API (see section 1), placing the headset by its first tracked pose (`VisionProPlacement`), the eye size taken from the first frame's texture (`fitStereoTargets`), culling once per frame, two eyes through `renderXR`, HZB, the left eye copied for the mirror, present.
- `CompositorFrameSource` / `CompositorFrame`: the adapter over `LayerRenderer` and `ARKitSession(device:)` + `WorldTrackingProvider` (last anchor kept when a query misses; `queryDrawables()` since `queryDrawable()` is unavailable on macOS; a second drawable, if any, is presented blank). `VisionProLayerConfiguration`: `.dedicated`, no foveation, `bgra8Unorm_srgb`, `depth32Float`.
- `VisionProPreviewBridge` / `VisionProPreviewActions` (in the toolbar's background): hand `openImmersiveSpace` / `dismissImmersiveSpace` / `supportsRemoteScenes` to the session.
- `ViewportCameras.isLockedPreview` and `steered` take the headset into account (`isPreviewingOnHeadset`, a closure tests replace); the editor's render extension therefore adds only the clear pass. `VisionProPreviewLabel` over the viewport with Stop.
- Tests: placement math, the loop with fake frames (real engine render into textures, pixels read back), the session's state machine with a live fake source on a thread, the menu table, the gates. Not covered: `CompositorFrameSource` and the SwiftUI scene, which need the headset.
- **The executable's identity.** The user's first try (2026-10-06) crashed on the menu item: `openImmersiveSpace` on macOS presents Apple's device picker, and its initializer (`DeviceDiscoveryUI.DevicePickerViewMacOS.init(… bundleIDToLaunch: …)`) traps when the main bundle has no identifier. An editor run from `.build` or from Xcode is a bare executable with no Info.plist. Reproduced here without a headset (the request goes out as soon as nothing plays; the trap is at the same address), fixed by embedding `Sources/UntoldEditor/Info.plist` into the binary (`-sectcreate __TEXT __info_plist` in the manifest's linker settings, `unsafeFlags`, allowed in a root package; `swift build` and Xcode's build system both embed it). With it the picker comes up and the session waits in `connecting`; the launch line logs the identity (`com.untoldengine.studio`, the same as the packaged app's). The settings follow the identity: `EditorSettingsDomain.adoptLegacySettings()` copies, once, what the old domain `UntoldEditor` holds that the new one lacks. The outcome of a request that does not open (cancelled, error) is logged.
- **An app bundle, registered.** The second try (same day) listed the Vision Pro in the picker, but selecting it failed twice: the picker asks LaunchServices for the app's name by bundle identifier (`_LSBundleCreateNode` −43, "Unable to get app name for bundle ID", `DDUIError` 10), which a bare executable has no record for, even with the identity embedded; the user cancelled and the request came back as `.error` (`AppStateController.Error` 5). So the editor has to run as an app bundle that LaunchServices knows. `scripts/dev-app.sh [--run] [debug|release]` (and `make run-app`) wraps the build in `Untold Engine Studio.app` inside the build folder: the executable copied (LaunchServices resolves the running file's real path, so a link does not do), the resource bundles linked and their files flattened in (the editor's and the engine's `Bundle.main` lookups), the exporter scripts linked, a `BuildProducts` link that `ComponentSDK.resolve` and `EditorEnginePackage.resolve` follow (tests), the bundle registered with `lsregister -f`. Verified here: no LaunchServices complaint from the editor or the picker, thumbnails and shaders found, the request waits in `connecting` with the picker up; the packaged app of `create_app_bundle.sh` has the same identity and works too. Xcode's Run still starts a bare executable: for the headset, start the editor with the script.
- **The mirror's pipeline and the viewport's depth.** The third try (same day) showed the scene in the headset, and the Mac crashed in `VisionProMirror.draw(in:)`: Metal's validation refused a pipeline with no depth format against the viewport's drawable, which comes with a `depth32Float` attachment (Xcode runs with the validation on). The pipeline now names the view's depth and stencil formats (`pipelineDescriptor(colorFormat:depthStencilFormat:library:)`), the pass leaves both untouched, and `encode(into:…)` draws into any pass, so a test draws the eye into its own colour and depth textures and reads it back; run with `MTL_DEBUG_LAYER=1` the test fails exactly as the editor did before the fix.
- **After the first working session (2026-10-06, the user's three asks).** (1) A preview control in the toolbar beside the build target, with a gap: `PreviewControl` (an `EditorPillTextButton`, wide enough to hit with the headset on, lit while the preview goes on; "Preview" / "Connecting…" / "Stop Preview"), hidden where the Mac has no destination; `PreviewDestination` names where a preview can show (Apple Vision Pro today; a window of its own and the full screen are the next ones, and the chevron to choose appears once there are two). (2) The keys and the mouse fly the camera while the headset previews: `ViewportCameras.steered` is the editor's camera then (the pointer stays locked out of selection and the overlays stay off), the mirror runs the editor's per-frame input before each viewport frame (the engine's `runFrame` would, and the headset's loop does not), and the loop re-reads the camera's pose every frame, keeping the headset's first tracked pose on it: the headset rides the camera. The camera is no longer put back at the end: it stays where it was flown.
- **The flying's first build made the user dizzy (eyes apart, the world swimming).** Cause: the loop called the engine's `setXRCameraWorldPosition` every frame, as the engine's own loop does so that streaming and LOD follow the head; it writes the head's position into the active camera, and that camera's pose was now read back every frame to place the headset, so every head motion fed back into the placement and grew frame after frame. Also, `getCameraEye`/`getCameraTarget` return what `cameraLookAt` wrote last; the fly keys and the mouse move the camera's position and rotation without touching them. Fix: no head position is written into the camera (streaming, LOD and shading go by the camera, which the headset stays within a room of; D8), and the pose is read from the camera's position and rotation (`VisionProPlacement.pose(of:)`). Tests: the pose follows `moveCameraBy` and `rotateCamera`; a head that moves between frames leaves the placement and the camera alone.
- **The second flying build: one eye head-locked, the other a mix.** Cause: the engine keeps the camera's view matrix in the camera itself; `renderXR` sets it per eye and the passes read it, and the editor's per-frame input (now run from the mirror on the main thread) rewrites it from the camera's own pose every viewport frame, even for a zero move (`translateBy` → `syncCameraTransformIfNeeded`). A rewrite in the middle of an eye draws part of that eye from the camera's own view, stuck to the head. Fix: `VisionProPreviewState.cameraLock`, held by the loop from the placement through both eyes, and by the main thread for every move of the camera from the keys (the mirror's per-frame input) and the mouse (the right button, the wheel, the pinch: `steerCamera` around the canvas handlers), only while a headset previews. Tests: the fake frames record that the camera was held when presented; `steerCamera` holds the lock only while previewing. (D9)
- **After the second working session (the user: level flying, less lag, Escape).** The keys fly the camera inside the loop now, one step per headset frame by the time since the last (`VisionProFlight`): level, W and S along the floor wherever the camera tilts, A and D aside, Q and E straight up and down, at the editor's speed (`speed × 6` a second). The mirror's per-frame hook only lets go of a fly key whose key-up was lost. The lag of the build before came from the flying on the main thread at the display rate, each step waiting for the eye render through the lock, and arriving at the headset in 60 Hz steps. Escape ends the preview from the moment it is asked for (a local key monitor the session installs while connecting or previewing); the label says so. (D10)
- **After the third working session (the user: along the floor whatever the tilt, the pointer as a second head, a message with the controls).** The trackpad gestures were still the editor's: the scroll orbited a point ahead and the pinch dollied along the tilted view, which is what climbed and dived. The user's intent: turn the view with the mouse, the Magic Mouse or the trackpad as a second head, on top of the real one, since looking back is hard sitting down. So, while previewing, the pointer is taken as a game takes it (`VisionProPointerCapture`: cursor hidden and held with `CGAssociateMouseAndMouseCursorPosition`, movement from a local event monitor, let go while the editor is not the active app): its plain movement turns the view, button or not, the same on the three devices; a scroll and a pinch do nothing then (a first build walked along the floor on them, and a Magic Mouse's surface walked the user about while they only meant to look); the editor's orbit, pan and zoom wait for the preview to end. Movement is the keys' alone. A card under the label lists the controls while previewing (`VisionProPreviewHints`). (D11)
- **W climbed to the ceiling, A and D drifted (the user, after the pointer round).** The engine's `updateXR` is `runFrame`, which runs the editor's per-frame input callback (`handleSceneInput`) from the headset's loop: the editor's own fly (`moveCameraWithInput`, along the camera's tilted axes) ran on top of the level step every frame. The earlier reading of the engine had the callback outside the XR path. Now `handleSceneInput` returns at once while a headset previews: the loop flies level, the pointer turns, the gizmo takes no input. Test: with W held and the camera looking up, the editor's own frame moves nothing while previewing, and climbs without.
- **Harold's review of #153 (2026-10-07), three points, none blocking.** (1) `stopLoopAndRestore` went on after its two-second wait and took the stereo targets, the mirror and the pointer from under a loop still in its frame: now the wait is `loopStopTimeout` (tests shorten it), a timeout is logged, the session stays in `ending` and the editor is put back when the loop's thread ends (`restoreWaitsForTheLoop`, `loopDidEnd`); the loop's own strong references kept the mirror alive all along, the hazard was `leaveStereo` re-making the targets. (2) A drawable beyond the first was presented with whatever its textures held: every drawable gets the anchor and the extra ones are cleared before being presented. (3) Two pass descriptors with `min(index, …)` would have clobbered eye 1 for a third eye: the loop draws the first two eyes, the engine's stereo, and says once when a frame brings more. Tests: a loop held in its frame outlives the stop and the editor is put back when it ends; a three-eye frame draws two and leaves the third untouched.
- The request is refused while anything plays, and that includes explore mode (the editor without a project open, which plays its demo scene): the menu item is disabled until a project is open.

## 6. Risks

| Risk | Mitigation |
|---|---|
| No Apple Vision Pro at hand while building: the compositor path cannot be run here. | The loop runs on a frame source protocol; tests render into their own textures and read them back. The compositor adapter is thin and is tried on the user's headset. |
| The engine's world is mutated from the main thread (panels, undo) while the loop renders on its thread. | The same as every visionOS game: entity creation and removal go through the engine's gates and `finalizePendingDestroys` runs inside the frame; transform edits are plain writes of value fields. |
| `@_weakLinked` is an underscored attribute. | It is what the Swift overlays of these frameworks use themselves; `-weak_framework` through `unsafeFlags` is the fallback, allowed in a root package. |
| `unsafeFlags` in the manifest (the embedded Info.plist). | Allowed in a root package and for Xcode's local packages; a package that depended on the editor could not use it, and none does. An incremental build does not notice a change to the plist file. |
| The remote stream shows artifacts and stalls (Apple's known issues). | Out of our hands; noted in the UI's help text. |
